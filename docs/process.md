# Процесс изменений: ветка → проверки → предпросмотр → слияние человеком

Описание процесса. Настройки GitHub в нём — решения владельца, из кода они не включаются.

## Путь изменения

1. **Ветка.** Работа идёт в ветке (`feature/...`, `fix/...`); прямой пуш в `main` не используется.
2. **Проверки (`.github/workflows/ci.yml`)** запускаются на каждый пуш в ветку и на каждый запрос слияния (pull request):
   - `test` — `npm test` в трёх поясах процесса: `UTC`, `Europe/Moscow`, `America/Los_Angeles`. Сутки смены всегда московские, поэтому результат от пояса машины зависеть не должен;
   - `build` — `npm run build` и проверка, что в репозитории нет выгрузок данных (`*.csv`, `*.xlsx`).

   Те же шаги локально: `cd web_app && npm ci`, затем `TZ=UTC npm test` (и два других пояса), `npm run build`.
3. **Предпросмотр.** Vercel сам создаёт Preview для ветки и запроса слияния. Перед слиянием человек открывает его и проверяет изменённое место на экране.
4. **Слияние делает человек** (владелец или назначенный им): проверки зелёные, предпросмотр просмотрен, приложены сравнение «до/после» (тестировщик) и цифры по данным (аналитик).
5. **`main` → выкладка.** Слияние в `main` запускает `main.yml` (тесты, сборка, GitHub Pages) и Production-сборку Vercel. Правки собираем в группы и сливаем по готовности: каждая выкладка ломает вкладки, открытые до неё.

Автоматического слияния нет и не предполагается.

## Что делает владелец в настройках GitHub

Ничего из этого не включалось и не меняется из кода.

- **Защита `main`** (Settings → Branches → rule для `main`): Require a pull request before merging; Require status checks to pass — отметить `test (TZ=UTC)`, `test (TZ=Europe/Moscow)`, `test (TZ=America/Los_Angeles)`, `build`; Require branches to be up to date; запретить принудительный пуш и обход правил; при желании — минимум одно подтверждение.
- **Vercel:** Production Branch — `main`; по возможности включить ожидание проверок GitHub перед Production (зависит от плана).
- **Приватность репозитория.** Если реальные выгрузки когда-либо были опубликованы, решает владелец: оставить репозиторий закрытым, запросить у поддержки GitHub удаление кэшированных ссылок на старые коммиты. Включить Secret scanning и push protection (Settings → Code security).
- **Секреты** (Settings → Secrets and variables → Actions). Сейчас нужен только `ANTHROPIC_API_KEY`, и то лишь для `agent.py` в `main.yml`. Если генерация кода больше не нужна, удалить секрет вместе с задачей `generate`. В файлах репозитория секретов быть не должно.
- **Задача `generate` в `main.yml`.** Ручной запуск с `force_regenerate=true` перезаписывает `web_app/` и пушит результат в текущую ветку (с `main` — сразу в Production). Решить: убрать задачу или оставить с запретом запуска из `main`.
- **GitHub Pages.** Если нужен, включить Settings → Pages → Source: GitHub Actions; если нет — убрать шаги Pages и задачу `deploy` (сейчас они молча пропускаются).

## Данные

Реальные выгрузки (ФИО, идентификаторы) в репозиторий, в CI и в отчёты не попадают; в тестах и проверках — только синтетические данные. Для ночных прогонов на реальных выгрузках нужно закрытое хранилище вне репозитория (каталог на сервере с ограниченным доступом или приватное хранилище), в CI оно подключается секретами. Где оно будет, кто имеет доступ и сколько хранить — решение владельца.
