## 2. Выкладка (Vercel, GitHub Pages)

### 2.1 Два `vercel.json`

`vercel.json` (корень) и `web_app/vercel.json` — **байт-в-байт одинаковые** (один и тот же git-объект `0d199b2d…`, `git ls-files --stage`), последнее изменение — 2026-06-11 (`464a546`).
Vercel читает `vercel.json` из «Root Directory» проекта. В корне нет `package.json` (там `agent.py` и `requirements.txt`), значит, чтобы Vite собирался, в проекте Vercel почти наверняка указан Root Directory = `web_app` — тогда используется `web_app/vercel.json`, корневой не читается. Подтвердить нельзя: настройки проекта недоступны (вопрос владельцу). Любая правка должна вноситься в оба файла или один из них нужно удалить, иначе они разойдутся.

### 2.2 Правило `rewrites` и запрос несуществующего воркера

Правило: `{"source": "/(.*)", "destination": "/index.html"}`. Клиентского роутера в проекте нет (в `package.json` нет `react-router`), так что правило ничего полезного не делает.
Расчёт по правилу (файлы из `dist`; логика «сначала файловая система, затем rewrite» — поведение Vercel по документации, на живом сайте не проверено; такой же «SPA-фолбэк» есть у `vite preview`: `curl /assets/optimizer.worker-OLD.js` → `200 text/html`):

| Запрос | Файл есть? | Ответ при текущем правиле | Ответ при исправленном (предложение) |
|---|---|---|---|
| `/assets/optimizer.worker-BoYYCvVw.js` | да | файл | файл |
| `/assets/optimizer.worker-OLDHASH1.js` (старая сборка) | нет | **200, `text/html`, тело `index.html`** | 404 |
| `/assets/index-OLD12345.js` / `.css` | нет | 200, `text/html` | 404 |
| `/demo/missing.json` | нет | 200, `text/html` (`r.json()` упадёт на `<`, а не «HTTP 404») | 404 |
| `/favicon.ico`, `/robots.txt` | нет | 200, `text/html` | 404 |
| `/assets/` | нет | 200, `text/html` | 404 |

Эксперимент в браузере (`exp_worker.mjs`): серверу задан тот же алгоритм; страница загружена, демо-данные (CSV) открыты, затем файл воркера удалён («выкладка»), нажато «Запустить оптимизатор».

| Режим сервера | Ответ на `/assets/optimizer.worker-….js` | Что произошло |
|---|---|---|
| как сейчас (`rewrites`) | `200 text/html` | воркер создан, браузер отвергает «не-JS» как модуль → событие `error` (пустое «worker error»); сработал откат: на экране «Фоновый расчёт недоступен (страница, скорее всего, устарела…)», расчёт выполнен в самой странице |
| исправленный (404) | `404 text/plain` | то же самое: событие `error`, тот же откат |

**Вывод (корректирует `devops.md`, где корень назван в `rewrites`):** исправление `rewrites` само по себе вкладку со старой сборкой не вылечит. Причина — ленивое создание воркера (`App.jsx:913`, `new Worker(new URL('./optimizer.worker.js', import.meta.url))` при первом расчёте) плюс удаление старых хэшированных файлов при выкладке. `rewrites` ухудшает симптом: ответ 200 вместо 404 скрывает проблему от мониторинга, возможен кэш HTML под адресом скрипта, ошибка в консоли вводит в заблуждение. Откат `db2d9cb` защищает от потери результата, но расчёт 8–24 с тогда идёт в потоке страницы — интерфейс замирает.

### Что нужно для пула `worker_threads` (взгляд эксплуатации)

- **Протокол уже есть:** `optimizer.worker.js` принимает `{id, kind, payload}` и возвращает `{id, result}` / `{id, error}` для задач `run`, `changes`, `gap`. Для Node нужна замена `self.onmessage/postMessage` на `parentPort` — ядро не меняется. `Date` в `tasks` сохраняются через `structuredClone` (в HTTP/JSON — нет, нужно восстановление дат; 15,3 МБ JSON на все задачи).
- **Размер пула:** число ядер − 1 (на этой машине 4 ядра → 3 потока); один поток = одна задача (CPU-bound, ≈ 100 % ядра на время расчёта); память ≈ 60 МБ данных + 50–180 МБ на расчёт на поток → планировать ≈ 300–400 МБ на поток.
- **Кэш данных в потоке:** держать разобранные `tasks/staffDB` по `dataVersion` (по образцу `resolverKey` в воркере), на запрос передавать только окно и изменения (1,16 МБ вместо 15 МБ).
- **Очередь и отказы:** очередь с ограничением длины и приоритетом (`applyChanges` — интерактив, `planWindow` — тяжёлый); тайм-аут = завершение потока и запуск нового; повтор максимум один; при исчерпании — ответ «план текущей версии без изменений» + признак `degraded`.
- **Версионирование:** `dataVersion` (хэш выгрузки + набор допусков), `planVersion` (хэш `id:employee`; в замере — 8 символов md5), `policyVersion`, `codeVersion` (коммит); план хранится как «версия + дельты» (журнал изменений `changes`), чтобы можно было воспроизвести.
- **Журнал событий:** на каждый запрос — запись `{requestId, kind, dataVersion, planVersion, windowDates, tasksInWindow, ms{…}, terminationReason, violations, queueWaitMs, workerId, rssMB}` (без ФИО; идентификаторы — хэшированные).
- **Масштабирование:** вертикально (число ядер) до очереди ≈ 3 параллельных тяжёлых расчётов на 4 ядра; горизонтально — по смене/подразделению (расчёты независимы); хранилище плана — внешнее (СУБД/объектное хранилище), не память процесса.

## 7. Процесс

### Как путь устроен сейчас

```
правка (агент/человек) → коммит → push в main И в claude/clever-ptolemy-t83pbr
   ├─ GitHub Actions: тесты + сборка (≈ 72 с) → Pages не публикуется (п. 1.3), результат ни на что не влияет
   └─ Vercel: Preview (ветка) → через ≈ 1 мин Production (main), без ожидания CI
```

Доказательства: пары запусков CI с одним `head_sha`; Production-развёртывание Vercel на каждый коммит `main`; PR только 2 (июнь); `main` и рабочая ветка указывают на один коммит (`e583185`) (`gh api …/branches`: `protected: false` у `main`).

| # | Серьёзность | Риск | Предложение | Трудозатраты |
|---|---|---|---|---|
| 7.1 | критично | Прямой пуш в `main` = мгновенная выкладка без проверок; сломанные тесты не блокируют прод | Процесс ниже; защита ветки включает владелец | 0,5 ч + решение |
| 7.2 | важно | Выкладка после каждой правки ломает открытые вкладки (п. 2.1, 2.4) | пакетирование релизов: сливать в `main` по готовности группы правок, не после каждой | — |
| 7.3 | важно | Нет проверки «как выглядит» до пользователя | Предпросмотр Vercel уже создаётся на каждый коммит ветки (бот `vercel[bot]`, среда Preview) — использовать его как обязательный шаг | 0 ч |
| 7.4 | важно | Нет замера и интерфейсной проверки в процессе | см. п. 1; `web_app/bench` отсутствует | 4–8 ч |

### Предлагаемый процесс «ветка → проверки → предпросмотр → слияние человеком»

1. Программист работает в ветке `feature/*`; пуш не затрагивает `main`.
2. Открывается PR в `main`. Автоматически: CI (`pull_request`) — `npm ci`, `npm test` на Node 22 (при желании и на 20), сборка в двух вариантах (`/` и `./`), проверка бюджета размера бандла, `npm audit --omit=dev` (с разрешёнными исключениями), поиск секретов, запрет данных в `public/`, смоук-проверка интерфейса (Playwright), синтетический замер с порогом по времени и числу нераспределённых.
3. Vercel создаёт Preview для PR; ссылка добавляется в PR.
4. Тестировщик прикладывает сравнение «до/после»; аналитик — цифры по данным.
5. **Слияние делает только человек** (владелец): обязательные проверки зелёные, не менее одного подтверждения, запрет прямого пуша в `main` и принудительного пуша — настраивает владелец (я только описываю: Settings → Branches → rule для `main`: Require a pull request, Require status checks, Require branches to be up to date, Do not allow bypassing).
6. Production — только из `main`; для слияний без изменений в `web_app/` сборка Vercel пропускается (п. 2.4); группировка релизов (п. 7.2).
7. После выкладки: проверка версии на странице, вкладка со старой сборкой получает баннер «Доступна новая версия» (п. 2.1).
