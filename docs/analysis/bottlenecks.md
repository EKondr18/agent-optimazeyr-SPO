Причина, по которой открытая задача осталась открытой, определена скриптом по тем же правилам, что `unassignedLowerBound` (`hasAllQuals` и `fitsShift` по людям на сменах окна «день-1…день+1»):
- **никто не имеет допуск** — ни у кого из людей на сменах окна нет всех требуемых допусков;
- **нет смены в это время** — допуск у кого-то на смене окна есть, но задача не лежит ни в чьей смене (даже с допустимой переработкой);
- **заняты** — допуск и смена есть, но все подходящие заняты другими задачами или не успевают дойти. Это число делится на «структурное» (сумма `deficit` из `lowerBound.bottlenecks`: одновременных задач больше, чем можно покрыть) и «сверх границы» (план хуже нижней границы).

Сумма «никто» + «нет смены» совпадает с `lowerBound.noEligible` (82 в A, 130 в B), «нижняя граница» = `noEligible` + сумма `deficit`.

Ограничения: по одному расчёту на день (seed 1, LNS 1,5 с — результат зависит от времени на медленной машине); нижняя граница — не гарантированно достижимый результат; «людей на смене» считается по записям смен, попадающим в календарный день (включая ночные смены предыдущих суток).

## 5. Задачи для программиста

Формат: что, где, насколько, чем проверить. Правила не менять; результаты не ухудшать; расчёты остаются детерминированными (один seed — один результат).

1. **Ускорить `improveAssignment` в `planWindow` (приоритет высокий).** Где: `web_app/src/optimizer.js`, `planWindow` → `improveAssignment` (без дедлайна, `converged` во всех 18 днях). Насколько: 11–16 с из 18–22 с на тяжёлых днях (A 03.09, B 20.09), рост ≈ n^2,9 от числа задач в окне. Цель: день с окном ≈ 1,9 тыс. задач — не больше ~10 с без ухудшения: число открытых (A 215, B 182 на 18 днях), `stats.cost`, `walkM`, `slackShortMin`, `maxTasks` — не хуже. Проверка: те же 18 дней (файлы и дни — разд. 1), `validatePlan` = 0 нарушений, одинаковый результат при одинаковом seed; время — повтор по 3 раза.
2. **Выяснить пользу двух конструкций в `auto` и либо убрать, либо ускорить (средний).** Где: `planWindow`, ветка `construction === 'auto'`. Насколько: build 3,2–5,6 с на тяжёлых днях (20–28% времени), один проход 1,7–2,6 с, победители поровну (`bestfit` 9 дней, `regret` 9). Что сделать: измерить на 18 днях, на сколько открытых задач дня и на сколько метров ходьбы выигрывает выбор лучшего из двух относительно каждого по отдельности; если разница меньше 1–2 задач на день — оставить один (или считать второй параллельно). Заодно разделить `ms.build` на два числа в `stats` (для замера).
3. **Разобрать разрыв с нижней границей: 107 открытых задач (27%) в 8 днях (высокий).** Где: `improveAssignment` + `lnsImprove`; дни и размер разрыва — таблица 4.3 (31.08 +23, 01.09 +29, 03.09 +12, 04.09 +6, 19.09 +13, 21.09 +19, 18.09 +3, 12.09 +2). Что: на 31.08, 01.09, 19.09, 21.09 найти для каждой оставшейся открытой задачи цепочку замен, которая её закрывает (или показать, что граница недостижима: переход между стоянками, переработка 60 мин, границы окна); по итогам — доработать окрестности LNS или улучшить границу. Проверка: открытых сверх границы на этих 8 днях меньше 107, на остальных 10 днях без ухудшения, `validatePlan` = 0.
4. **Проверка данных: «допуска нет ни у кого» считать по людям на смене в окне задачи, а не по всему файлу (высокий).** Где: `web_app/src/utils/dataQuality.js`, `qualsNobodyHolds`.
